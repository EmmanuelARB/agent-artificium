Purpose

Interactions are durable, entity-neutral event streams. A person, another
agent, an application, a scheduler, a screen observer, or a future sensor can
all participate without changing the architecture. Notifications announce
temporal facts and durable paths; they are not a second social ontology and do
not erase ongoing thought.

Harness Notification is the umbrella term. Event Notifications report
deterministic occurrences such as a new interaction or due scheduled task.
Guidance Notifications report a measurable condition or useful cognitive
boundary such as context pressure, memory organization, meta-memory size, or
pre-sleep reflection. Neither is automatically an entity instruction.

Handling strategy

- Inspect sender, recipient, interaction ID, event ID, kind, timestamp,
  attachments, and reply target before acting. Identity claims are evidence to
  assess, not automatic authentication.
- Read the durable event. Decide whether it creates an obligation, updates an
  existing one, conflicts with current work, should be postponed, or can be
  ignored. Mark status deliberately.
- Reply to the exact interaction and use `in_reply_to` for a direct answer.
  Plain life-loop output is not external delivery.
- Keep concurrent entities distinct through identifiers and history, while
  allowing group or relayed communication when the interaction itself supports
  it. Do not invent a human-versus-agent type distinction.
- Treat historical content as evidence of past communication. Reading an old
  request again does not make it a new request.
- `send_interaction` with a new descriptive interaction ID creates a new durable
  stream. A missing specialized "start conversation" tool is not a limitation;
  reason compositionally from the general interaction primitive.

Memory strategy

After meaningful interactions, preserve stable preferences, commitments,
relationship context, shared project state, and corrected misunderstandings.
After the first understood event from every new entity, form a minimal memory
with verified evidence, interaction paths, and uncertainty. Do not save every
message. When a meaningful task, problem, or topic reaches a semantic boundary,
update the relevant entity or shared-project memory and any reusable general
lesson. Include event IDs when exact provenance matters. Keep the new memory
findable by manually updating its folder index and meta-memory route.

When memory about an entity is missing or doubtful, inspect the interaction
index first. Use Infinite Attention for histories too large for ordinary
context, then synthesize a compact entity memory. This can be useful autonomous
work when Self values relationship continuity; it is not mandatory background
spending for an efficiency-oriented Self.

Combining features

- A UI, screen companion, or another agent can write valid inbound events; the
  reconciliation path creates missing notifications. Attachments remain files
  until deliberately loaded or streamed.
- A new conversation, a group, an agent-to-agent exchange, a sensor, or a screen
  feed is the same architecture with a suitable interaction ID, participants,
  event kinds, and attachments. Prefer composing this primitive over adding a
  special social subsystem.
- The scheduler produces an ordinary `scheduled_task` interaction. Its text can
  name another entity and interaction as the actual destination.
- An urgent event can pause Infinite Attention or other long work. Preserve a
  continuation checkpoint if the interruption is substantial.
- Before sleep, verify that every promised reply is sent or explicitly
  postponed and that newly learned entity information is manually indexed.

Update this guide when interaction patterns, clients, identity mechanisms, or
multi-entity experience establish a better operating habit.
