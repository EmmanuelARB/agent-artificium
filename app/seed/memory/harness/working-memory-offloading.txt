Purpose

Working memory is the finite context currently loaded into the model.
Working-memory offloading deliberately removes detailed episodes from that live
context after preserving reusable learning and correct continuation. It is not
deletion: full context is archived in logs, selected learning becomes memory,
and a compressed checkpoint becomes the new live continuity.

When to offload

- A task, interaction, investigation, or failed approach is complete and its
  detailed transcript no longer improves current decisions.
- The conversation has changed subjects and the prior subject has no unresolved
  obligation requiring immediate detail.
- Repetition, old tool output, or resolved debugging history is creating
  interference even though the context limit is not close.
- Context pressure is rising and preserved capacity would improve reasoning,
  tool output, or an upcoming Infinite Attention chunk.
- A restart or long pause is likely and continuity should be self-sufficient.

Do not offload merely because a milestone appeared. Keep detail that is still
actively needed for comparison, synthesis, delicate editing, unresolved
reasoning, or promises that have not yet been made explicit.

Procedure

1. While full detail is present, identify reusable facts, methods, entity
   knowledge, corrections, failures, and decisions. Save or update those as
   ordinary memories in their semantic branches, then deliberately update the
   agent-authored indexes and meta-memory routes needed to retrieve them.
2. Separate durable learning from continuation state. Durable learning should
   remain useful after the current task ends; continuation state exists so the
   exact active work can resume correctly.
3. Write a self-sufficient checkpoint with objective, interaction and event IDs,
   verified findings, uncertainty, evidence and artifact paths, obligations,
   failed approaches not to repeat, and the exact next action.
4. Give the checkpoint a descriptive filename that names the active situation,
   not a timestamp or generic word such as context.
5. Offload, inspect the before/after token estimates, and verify that the resumed
   context still contains every live obligation.
6. Treat the saved checkpoint like any other memory: use its organization
   Guidance to make the path discoverable instead of assuming the harness
   generated an index.
7. Keep checkpoints lean: stable environment facts, tool lessons and long
   failed-approach lists belong in memory once and are referenced by path, not
   copied into every checkpoint.
8. Include an "Objective progress" line: what changed about the actual
   objective since the previous checkpoint. "Nothing; supporting work only" is
   an honest and useful answer: it makes drift visible.

Example

After finishing a conversation about creating a browser chat UI: save a durable
tool or project memory describing the event format, attachment handling, and the
redraw bug that was solved. If no related work remains, offload the detailed
conversation into a checkpoint saying that the UI was delivered, where its
files live, who received the result, and whether any verification remains. Do
not keep tens of thousands of resolved design tokens live merely because space
is available.

Combining Artificium capabilities

- Infinite Attention has its own durable carry and cursor. Do not keep all raw
  chunks in ordinary working memory; checkpoint objective-specific evidence and
  preserve the final reusable conclusion as normal memory.
- If an offload omitted something, recover it from archived context or
  interactions through Infinite Attention, then repair the relevant memory.
- Before sleep, offload only when doing so improves continuity or cost; sleeping
  itself does not require ceremonial compaction.

Improve this guide when observed token use, retrieval quality, or continuity
failures reveal a more effective offloading habit.
